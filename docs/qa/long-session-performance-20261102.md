# 오래 플레이할 때의 속도 최적화 — 2026-11-02

이미지·음악 파일을 바꾸거나 해상도·음질을 낮추지 않고, 오래 플레이할 때 남는 참조와 반복 검색을 줄였다. 저장 형식, 항해 속력, 게임 시간의 최대 보정값은 유지한다.

## 재현한 원인과 수정

- `js/art/reel.js`가 읽은 발견 장면 판과 완료된 Promise를 영구 보관했다. 공통 그림 캐시에서 지워도 이 참조가 원본을 붙잡았다. 이제 진행 중인 읽기만 공유하고, 칸 정보는 원본 이미지에 `WeakMap`으로 연결한다. 원본의 보관과 미리 풀기는 `G.Img`에서만 관리한다. 재생 중인 장면은 자기 참조를 유지해 끝까지 원본으로 재생한다.
- `js/core/images.js`는 그림 900장만 제한했다. 장면 판은 한 장도 약 10~14MiB라서 이보다 훨씬 일찍 메모리가 커졌다. 원본 가로×세로×4로 계산한 픽셀 보관 예산 256MiB를 함께 적용한다. 넘으면 오래 안 쓴 참조부터 예산의 80%까지 놓는다. 현재 사용하는 이미지의 크기나 주소를 바꾸지 않으며, 다시 찾으면 같은 원본을 읽는다. 예산보다 큰 단일 원본은 읽기 반복을 막기 위해 한 장 유지한다.
- `js/ui/hudpin.js`의 판 목록은 창 크기를 바꿀 때만 이전 화면을 정리했다. `UI.clearScreen()` 직후와 새 판 등록 시 연결이 끊긴 참조를 정리하고, 같은 요소의 중복 등록과 사라진 판의 끌기도 막는다. 자리 기억·끌기·오른쪽 클릭 복원은 유지한다.
- `G.Img.list()`는 요청마다 전체 이미지 목록을 다시 훑었다. 파일 키와 최근 접두어 목록 64개를 보관한다. 반환할 때 복사해 호출자가 고친 배열이 다른 화면에 영향을 주지 않게 하고, `G.Img.reset()`에서 함께 초기화한다.
- `js/main.js`에서 프레임 시간에 따른 바다 해상도 자동 하향·복원을 제거했다. 사용자가 고른 `settings.res`와 화면 배율을 그대로 사용해, 성능 문제 때문에 화질이나 그래픽 버퍼 크기가 왕복하지 않는다.

조정값은 `js/data/seafx.js`의 `G.FX.img.keep`, `keepBytes`, `trimRatio`, `listKeep`에 있다. 음악·효과음·이미지 원본 자산과 음원 재생 코드는 수정하지 않았다.

## 같은 조건의 전후 검사

설치된 Chrome, file://, 960×540, 하드웨어 그래픽으로 `tests/long_session_perf.cjs before` / `after`를 실행했다. 발견 장면 판 48개를 두 차례 순서대로 읽고, 첫 판을 재생용으로 보유한 상태에서 다른 판을 다시 읽은 뒤 원본 복원도 검사했다. 새 UI 판 3개씩 100회 만들고 화면을 걷은 뒤 강제 GC를 거쳐 DOM을 셌다.

| 항목 | 수정 전 | 수정 후 |
|---|---:|---:|
| 발견 장면 판 48개 첫 회차의 보관 픽셀 추정량 | 540MiB | 243MiB |
| 같은 48개 두 번째 회차 | 540MiB | 232.9MiB |
| 화면 100회 교체 뒤 DOM 노드 증가 | +1,200 | 증가 없음(-54) |
| 같은 검사에서 이벤트 처리기 증가 | +1,800 | 증가 없음(-6) |
| 걷기 파일 목록 검색 300회, 7묶음 중앙값 | 360.4ms | 약 0.1ms |

픽셀 추정량은 게임 코드가 보유한 원본의 너비×높이×4 합계다. 브라우저 전체 사용량·애니메이션 내부 프레임·현재 장면이 별도로 보유한 그림·그래픽 장치 전체 메모리를 뜻하지 않는다. 노드 감소는 처음 페이지의 비동기 UI 정리도 포함한다. 목록 검색은 개별 작업의 비교이며 전체 게임의 FPS 증가율로 환산하지 않는다.

수정 후 장면 판의 원본 너비 3,456px·칸 너비 576px, 캐시에서 빠진 판의 재읽기, 이미 재생 중인 판의 마지막 장면 표시가 통과했다. 40ms 간격으로 게임 루프를 480회 진행해도 바다 캔버스는 960×540을 유지했다. 예전 검사 도중의 최저 해상도는 기록하지 않았으므로, 수정 전 마지막 값 1을 자동 하향이 없었다는 뜻으로 해석하지 않는다.
