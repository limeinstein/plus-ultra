# 항해 중 끊김 완화 (2026-11-01)

선박의 모형·해상도·그림자·돛·망루·출렁임을 유지하면서, 같은 프레임 안에서 반복하던 그래픽 버퍼 재할당과 사용하지 않는 선박 시트의 압축 해제를 줄였다.

## 원인과 수정

- 크기가 다른 선박을 번갈아 그릴 때 `WebGLRenderer.setSize`가 캔버스를 계속 줄이고 늘렸다. CPU 프로파일에서 너비·높이 변경에 긴 대기가 잡혔다. 이제 함대에 필요한 최대 버퍼를 재사용하고, 배마다 필요한 영역에 원래 픽셀 밀도로 그려 잘라 옮긴다.
- 확대를 줄이면 8프레임 동안 전체 함대의 최대 사용 크기가 버퍼의 72% 아래인지 확인하고 한 번만 축소한다. 큰 버퍼를 계속 유지하거나 작은 배를 그릴 때마다 재할당하지 않는다. 상세 감상 화면의 단일 선박 그리기는 필요한 크기를 바로 쓴다.
- 3D 모형이 정상적으로 표시되는 배도 큰 2D 시트를 풀고 반 크기 사본까지 만들고 있었다. 항해·해전·게임 준비 단계에서는 3D 사용 가능 여부를 보고 이 준비를 생략한다. 3D가 꺼졌거나 장치 손실·모형 생성 실패가 있으면 기존 시트를 준비한다. 도감 등 2D를 사용하는 화면의 호출은 유지한다.

변경 경로: `js/art/ship3d.js`, `js/art/shipsprite.js`, `js/data/seafx.js`, `js/main.js`, `js/scenes/sea.js`, `js/scenes/battle.js`. 조정값은 `G.FX.ship3d.bufferShrinkFrames`, `bufferShrinkRatio`. 항해 속력·게임 시간·저장 형식·수면 파도 식은 바꾸지 않았다.

## 같은 조건의 측정

Chrome / RTX 3050 / 1600×900 / 수면 해상도 1 / 기함·동행선 3척과 상선·해적·군함 3척. 배율별 12프레임 준비 후 90프레임을 측정했다. 기본·3배·근접은 같은 카메라에서 자세를 갱신하며 매번 실제 장면을 그린다. `update(1/60)` 제출 시간과 두 WebGL 장치의 `finish()` 완료 대기 시간을 따로 기록했다. 아래는 완료 대기를 포함한 값이다.

| 조건 | 수정 전 중앙값 / 95백분위 | 수정 후 중앙값 / 95백분위 |
|---|---:|---:|
| 기본 배율 | 10.9 / 14.4ms | 7.7 / 11.5ms |
| 선박 확대 3배 | 15.8 / 19.8ms | 7.3 / 9.1ms |
| 근접 9.1배 | 19.3 / 23.1ms | 8.0 / 10.8ms |
| 근접 후 기본 배율 복귀 | — | 6.9 / 8.3ms |

3배율 중앙값은 약 54%, 근접은 약 59% 줄었다. 안정된 프레임의 캔버스 너비·높이 변경은 각각 6회(버퍼 크기 변경 3번), 10회(5번)에서 0회로 줄었다. 축소 뒤 버퍼는 768→256픽셀로 돌아왔다. 측정은 특정 장치의 장면 처리 비용이며 디스플레이에 표시된 FPS나 모든 장소의 성능을 보장하는 값은 아니다. 최초 모형·셰이더 준비 비용은 위의 지속 프레임 수치에서 제외했다.

별도로 실제 이동을 120프레임 진행했다. 약 0.93° 이동 후 기함은 화면 x=760px 부근에 남아 해도가 따라왔으며, 지형은 분할 갱신 7회·교체 1회를 처리했다. 이 구간은 중앙값 10.9ms / 95백분위 15.1ms / 최대 25.6ms였다. 화면 밖으로 빠지는 주변 선박 수가 변하므로 위의 고정 6척 전후 비교와 직접 비교하지 않는다.
